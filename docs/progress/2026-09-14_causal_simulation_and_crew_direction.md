# Progress — causal simulation engine and simulated crew direction

Date: 2026-09-14  
Status: **architecture direction established; targeted research/build work next**

## Direction clarified

The next development phase remains focused on **test-harness validation**, not player-facing Mission Control station UI and not multi-human playtesting.

Two architecture boundaries were clarified:

1. the flight crew will be represented by the simulation rather than as another human player role;
2. the current PC+2 historical event sequence is a useful integration/validation scaffold, but it is not sufficient as the long-term scenario engine because player actions, omissions, timing, and mistakes must produce causal downstream consequences.

Decision D-020 records the crew boundary.

## Simulated crew

Initial CAPCOM↔crew handling may be deliberately simple and deterministic:

`CAPCOM transmission → crew receipt/acknowledgement → supported crew action → spacecraft consequence → crew report/derived observations`

The important constraint is separation of stages. A transmitted message does not itself alter spacecraft state. Crew reports do not expose hidden physical truth.

The existing facilitator buttons for crew receipt, crew shutdown, crew report, and physical response remain validation scaffolding. As supported crew actions are implemented, those steps should be generated by the simulated crew/causal engine rather than manually advanced by the facilitator.

## Causal simulation direction

Primary Apollo simulation sources support a closed-loop architecture rather than an exhaustive authored branch tree:

- Apollo mission simulation included trajectories, telemetry, uplink/voice communications, major spacecraft-system operation, simulated MSFN/MCC participation, and procedure verification;
- Apollo simulator controls/displays were active and closed-loop;
- instructor facilities supported malfunction insertion;
- Apollo engineering simulation used real-time mathematical/system models and hardware/software interfaces;
- mission-rule training explicitly addressed nonnominal situations for which complete responses had not been preplanned.

Research note 127 and `resources/source-catalog/APOLLO_SIMULATION_ENGINE_SOURCES.md` record this evidence and its limits.

The project target is therefore a **hybrid causal simulator**:

`scenario inputs + elapsed time + player/crew actions → authoritative state → instrumentation/telemetry/ground products → controller-visible information → further actions`

This does not mean immediately reproducing the entire LM/CSM at first-principles fidelity. Decision D-019 remains the admission rule: model enough causal detail to support the actions, failures, rules, and observations that gameplay exposes.

## Test-console cleanup

The facilitator test console was cleaned up without moving toward a final station UI:

- `READY` / `NOT READY` buttons are now labeled `REPORT READY` / `REPORT NOT READY`, making clear that each press intentionally creates a readiness report/audit event;
- the unused/misleading `SHUTDOWN ITEM ID` input was removed because the engine-off validation override never consumed it;
- the physical-response override now states explicitly that it forces a DPS engine-off response and consumes no CAPCOM item ID;
- static browser-contract tests cover these validation-surface expectations.

Repeated readiness events are therefore not currently treated as a backend defect: repeated reports are legal and useful at different mission times. The test UI now makes the event-producing nature of the action explicit.

## Next research/build boundary

Before player UI work or human playtesting:

1. perform a targeted archival/source search for Apollo CSM/LM mission-simulator functional descriptions, mathematical-model documents, malfunction-insertion/instructor manuals, and model-validation/correlation material;
2. use the recovered evidence plus spacecraft subsystem documentation to define one narrow causal-model contract;
3. use the existing PC+2 DPS/electrical/instrumentation chain as the first proving ground;
4. implement deterministic simulated-crew handling for the existing CAPCOM shutdown exchange;
5. extend the test screen so correct, omitted, late, and wrong actions can be exercised and their resulting state/observations inspected;
6. require consequences to emerge from state transitions rather than from pre-authored outcome labels wherever the modeled mechanism should determine the result.

Player-facing historical station UI and simultaneous human play remain deliberately later phases.
